# Dataset Observations

Generated by `analysis/explore_feed.py` from `ship_positions.json`.
Regenerate with `python analysis/explore_feed.py > docs/dataset-observations.md`.
For the same analysis with charts, open `analysis/explore_feed.ipynb`.

These are observations about the supplied data, recorded because they shaped
design decisions. They describe what the file contains, not what it should.

## `stationId` is a record identifier, not a receiving station

- Unique across all 2,696 records: **True**.
- Range 81–3396, with gaps.
- Strictly ascending in file order: **True**.

No value repeats even once across 18 hours and 3 vessels, which is not how a
receiving station behaves. It is treated as the Report ID (ADR-0001).

## `(mmsi, timestamp)` is not unique, and the duplicates conflict

- Only **345 distinct `(mmsi, timestamp)` pairs** across 2,696 records.
- **142 of those keys carry more than one record**, and **0 of them are exact duplicates**.
- The busiest single key carries **119 records**.
- Separation between the first two of each: median 59 km, max **515 km**.
- Keying on `(mmsi, timestamp)` would discard **2,351 records (87.2%)**.

The widest disagreement, one vessel at one second:

```
mmsi 247039300 @ 1372696620 -> stationId  734, 44.05453, 14.07790, speed 15.6 kn
mmsi 247039300 @ 1372696620 -> stationId 1643, 40.57935, 18.21955, speed 16.1 kn
```

Both are kept. The store records observations rather than adjudicating between
them (ADR-0001).

## Reported Time is heavily degenerate

- Only **219 distinct values** across 2,696 records.
- Every gap between consecutive values is a multiple of 60s: **True**.
- The busiest single value, 1372700580 (2013-07-01 17:43), carries **272 records**.

  - At that one second, MMSI 247039300 has 69 records spanning lat 39.50–44.24, lon 13.89–19.15.
  - At that one second, MMSI 311040700 has 84 records spanning lat 33.64–34.82, lon 31.46–35.54.
  - At that one second, MMSI 311486000 has 119 records spanning lat 36.26–38.21, lon 11.00–15.97.

A one-minute time filter can therefore return hundreds of reports scattered
across the Mediterranean. This is a property of the data, not of the API.
It also makes real-time replay undefined: there are no inter-arrival gaps to honour.

## Ordering by `stationId` recovers coherent voyages; by timestamp it does not

Consecutive-hop distance along each vessel's track under each ordering.

| MMSI | ordering | total path | median hop | p95 hop |
| --- | --- | --- | --- | --- |
| 247039300 | timestamp | 112,973 km | 79.06 km | 410.97 km |
| 247039300 | stationId | 94,421 km | 45.24 km | 395.31 km |
| 311040700 | timestamp | 41,070 km | 10.90 km | 263.74 km |
| 311040700 | stationId | 1,703 km | 0.60 km | 3.79 km |
| 311486000 | timestamp | 33,517 km | 7.30 km | 270.65 km |
| 311486000 | stationId | 597 km | 0.51 km | 0.76 km |

Independent corroboration: taking each report's own reported Speed, the time it
would need to cover the distance to the next report in `stationId` order is

  - MMSI 247039300: median **5601 s**
  - MMSI 311040700: median **79 s**
  - MMSI 311486000: median **67 s**

Two of the three land on the 60-second grid the timestamps use, which is what
you would expect if `stationId` is the true receipt sequence. MMSI 247039300
stays incoherent under both orderings, consistent with two vessels sharing one
MMSI - a real AIS phenomenon. Not investigated further; it changes no decision.

## Field ranges

| field | observed | note |
| --- | --- | --- |
| `speed` | 0–199 | knots x10; max is 19.9 kn |
| `course` | 10–355 | whole degrees, not the decidegrees AIS uses on the wire |
| `heading` | 4–357 | whole degrees |
| `rot` | {'': 2696} | the empty string in every record |
| `status` | {0: 2616, 5: 80} | navigational status |

`rot` never carries a value, so its column type comes from the AIS specification
(signed, -128..127) rather than from the data. A non-nullable column would
reject the entire dataset (ADR-0002).
